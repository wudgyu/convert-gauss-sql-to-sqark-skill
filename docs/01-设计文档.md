# gauss2spark 设计文档

## 1. 目标与非目标

**目标**：把一个 openGauss SQL 文件端到端转换为 Spark SQL，并让整个过程可审计、
可追溯——包括每条语句为什么这样转、依据是哪条规则、哪里需要人工确认。

**非目标**（明确不做，避免期望错位）：

- 不承诺转换结果可复现。同一输入两次运行可能得到不同结果，这与"由模型主导转换"的
  方案性质有关，见 §12 决策记录 D4。
- 不承诺结果已经过真实数据验证。静态可检出的错误做到零放行，语义等价性靠审核兜底，
  真实可用性需要在一侧有真实环境时另行验证，见 §8。
- 不支持 PL 块（`DO`、`FUNCTION`、`PROCEDURE`、`TRIGGER`）与 psql 元命令。
- 不绑定落点存储形态，不生成 `USING`、`TBLPROPERTIES` 等落点相关子句。

## 2. 适用边界与已知限制

| 项 | 值 |
|---|---|
| 源方言 | openGauss，`DBCOMPATIBILITY = PG` |
| 目标方言 | Spark SQL 4.2.0（唯一测试覆盖版本） |
| 语句范围 | SELECT、DML、常用 DDL 与命令；PL 块不支持 |
| 编码 | UTF-8（含 BOM）、GB18030、UTF-16LE、ISO-8859-1 兜底 |
| 大文件 | 超过 200 行或 20 条语句时启用分片器 |

已知限制见 §13 待验证清单。特别提醒：`SPARK_HOME` 对应的 Spark 版本若不是 4.2.0，
结论不适用，需重跑基线工具。

## 3. 总体架构

```
输入 SQL 文件
   │
   ├─ g2s split ─────────► statements.jsonl（切分、编号、偏移、sha256）
   │
   ├─ gauss2spark-analyze ─► 01_analysis.jsonl（分类、风险、档位、规则路由）
   ├─ gauss2spark-convert ─► 02_conversion.jsonl（改写 + 决策链）
   ├─ gauss2spark-review  ─► 03_review.jsonl（独立复核 findings）
   ├─ gauss2spark-fix     ─► 04_fix.jsonl（按 findings 修复，最多 2 轮）
   │
   ├─ g2s check   ─► 契约校验（字段、枚举、规则 id、阶段完整性）
   ├─ g2s gate    ─► 档位统计 + 审批比对，决定放行与否
   └─ g2s assemble ─► 05_final.sql、06_process-log.md、07_audit-report.md、
                      run_manifest.json
```

职责划分是这个设计的核心：

- **确定性工具**（Java，`g2s-core`）只做机械可判定的事：切分、编号、契约校验、
  闸门计算、产物组装。它不做任何语义判断。
- **模型**（六个 skill）做语义判断：识别、改写、复核、修复。
- **规则库**（YAML）是模型的知识来源，不是可执行代码。

## 4. 节点契约

节点之间的完整约定见 `contracts/workflow.md`，此处只列关键点。

| 节点 | 输入 | 输出 | 关键约束 |
|---|---|---|---|
| 编排 | 输入文件 | run 目录与全部产物 | 闸门不放行就不产出最终 SQL |
| 分析 | `00_input.sql` | `01_analysis.jsonl` | 不改写 SQL；档位取最严 |
| 转换 | 分析结果 + 规则库 | `02_conversion.jsonl` | 必须填满决策链字段 |
| 审核 | 源语句 + 转换结果 | `03_review.jsonl` | 先独立推导语义，再看转换者理由 |
| 纠错 | findings | `04_fix.jsonl` | 最多 2 轮；不得靠降档消除问题 |
| 规则 | —— | 规则库与 `index.json` | 无实测依据只能停在 candidate |

## 5. 数据契约

字段定义见 `contracts/artifact-contract.md`。设计上有三点值得强调：

1. **所有产物都是 UTF-8 的 JSON / JSONL**，没有 YAML。规则库是 YAML，但只由人
   和维护脚本读写，工具链只读由它生成的 `rules/index.json`，因此 Java 侧不需要
   YAML 解析库。
2. **`statement_id` 是全局锚点**。切分后编号一次，后续各阶段不得重编号，
   跨阶段对齐、审计追溯都靠它。
3. **`02_conversion.jsonl` 的字段即过程文档的数据源**。`understanding`、`strategy`、
   `alternatives`、`risks`、`evidence`、`source` 六项缺一不可，
   `06_process-log.md` 只是它的可读视图。

## 6. 分片与重组策略

切分器是整套方案里唯一"不自建就会出事"的部分，因为它的失败方式是静默的：
一个切分点若落在字符串字面量或美元引用体内部，两半都会变形，而且不报错。

词法层只在最外层遇到分号才断句，以下位置的分号一律视为普通字符：单引号字符串
（含 `''` 转义与 `E'...'` 反斜杠转义）、双引号标识符（含 `""` 转义）、
美元引用体（`$$` 与 `$tag$`）、行注释、嵌套块注释。另外识别 psql 元命令
（行首反斜杠）与 PL 块（含 `BEGIN/END` 深度保护）。

阈值路由：行数 ≤ 200 且语句数 ≤ 20 走 `direct`（整文件交给模型），否则走 `split`。
两种路径都产出 `statements.jsonl`，保证任何一条语句都能回溯。

注释归属规则：与分号同行的注释归上一条语句，其余注释归下一条语句的前导注释。
这个规则直接影响下一阶段的分类——早期版本曾因为行尾注释残留污染下一条语句的
主体，把一条 `SELECT` 误判成 `INSERT`。

## 7. 规则库设计

规则是数据，不是散文。`rules/` 下的 YAML 按主题分组：

| 文件 | 内容 |
|---|---|
| `core/010-type-mapping.yaml` | 类型名映射，含无精度 numeric 的高风险条目 |
| `core/020-ordering-null.yaml` | 排序 NULL 位置，头号漂移项 |
| `core/030-null-semantics.yaml` | `concat` 等 NULL 语义差异 |
| `core/040-scalar-functions.yaml` | 标量函数映射与"禁止改写"清单 |
| `core/050-datetime-format.yaml` | 日期格式 token 翻译表 |
| `core/060-ddl.yaml` | DDL 对象与表属性 |
| `unsupported.yaml` | 语句级不支持清单（权威） |

三条设计原则：

1. **档位决定放行**。`auto` 自动放行，`confirm` 与 `blocked` 一律进审批闸门。
2. **每条规则必须有实测依据**（`evidence` 字段）。没有依据的规则只能是 `candidate`，
   校验器会拒绝高风险改写规则设为 `auto`。
3. **规则库也记录"不要做什么"**。`core.functions.native` 列出了在 Spark 4.2 上
   原生可用、禁止改写的构造（`decode`、`nvl`、`string_agg`、`array_agg` 等）。
   这类规则存在的意义是拦住后来者"顺手优化"——实测显示这些改写不但多余，
   而且会让结果变错。

## 8. 校验与质量保证

分五层，前四层是确定性、可执行的，第五层由模型执行但受清单约束：

| 层 | 内容 | 实现 |
|---|---|---|
| L1 结构检查 | 括号引号配对、语句终止、元命令识别 | 切分器 |
| L2 方言残留扫描 | 类型名、函数、运算符、DDL 子句黑名单 | 审核清单（含误报例外） |
| L3 契约校验 | 字段完整、枚举合法、规则 id 存在、阶段完整 | `g2s check` |
| L4 构造校验 | 输出是否使用了不允许的构造 | 规则库 + 审核 |
| L5 独立审核 | 换视角重推语义、套用漂移清单 | `gauss2spark-review` |

**保真度分级**必须如实记录在 `run_manifest.json`：

```
static-only → syntax-parse → explain-checked → execution-verified
```

当前工具链实现到 `static-only`。Spark 解析器与 `EXPLAIN` 校验需要 `g2s-spark`
适配器，接口已留出但尚未实现，见 §13。

## 9. 闸门与人工确认

闸门判定的完整条件（`g2s gate`）：

一条语句需要审批，当且仅当满足其一：档位不是 `auto`；转换结果是 `blocked` 或
`needs_manual`；审核结论为 `block`；审核结论为 `revise` 且没有任何纠错记录。

最后一条是刻意加的：**审核要求修改但没改的语句不得静默放行**。

未满足时：不产出最终 SQL、退出码 3、输出待处理清单。只有显式 `--allow-partial`
才产出残缺版本，且文件头带醒目提示。

人工确认记录在 `approvals.jsonl`，三种处置：`accept-converted`（接受）、
`use-manual`（换人工 SQL）、`exclude`（排除）。三者都必须记录确认人与时间。

## 10. 过程文档与可追溯性

"看到模型是如何转换的"这一需求，通过 `02_conversion.jsonl` 的固定字段实现：
每条语句都要交代源端语义、采用策略、**考虑过但放弃的方案及原因**、风险自评、
证据片段、以及本次改写是规则驱动还是自由发挥。

刻意不导出原始思维链：它不可复现、无法校验，也构不成审计证据。审计需要的是
"决策依据可复查"，而不是 token 级的心路历程。`alternatives` 字段是最容易被省略、
也最有价值的一项——"为什么没选另一种写法"恰好是审查者最想知道的。

`source: llm`（自由发挥）不是错误，但审核节点会逐条严查，审计报告会单独统计条数。

## 11. 跨 CLI 适配与分发

六个 skill 是纯 Markdown，符合通用 Agent Skills 规范，可用于 claude、codex、
opencode、trae、codebuddy 等宿主。它们的调用对象是仓库根下的 `g2s` 脚本。

因此工作流要求**六个 skill 与仓库一并可用**，不支持把单个 skill 拷到别处使用：
skill 正文里引用的 `contracts/`、`rules/`、`checklist/` 一律按仓库根解析，
而不是相对 skill 文件位置解析。

工具构建产物（`tools/bin/*.jar`）不入库，由 `tools/build.sh` 生成；
运行产物（`runs/`）与未脱敏语料（`tests/local/`）都在 `.gitignore` 中。

## 12. 设计决策记录

| 编号 | 决策 | 理由与代价 |
|---|---|---|
| D1 | 放弃全自建引擎，改为模型主导转换 | 规则覆盖面永远追不上真实语料；代价是失去可复现性 |
| D2 | 保留确定性内核做切分、编号、重组 | 切分的失败是静默的，必须由代码保证 |
| D3 | 规则保持结构化 YAML，不写成散文 | 保住增删改查、版本与溯源；代价是回归要靠评测而非断言 |
| D4 | 接受"可追溯但不可复现" | 模型转换的固有性质；用固定字段的决策记录补偿 |
| D5 | 工具链选 Java 而非 Go 或 Python | JVM 是 Spark 的硬依赖，不新增运行时；jar 是单一产物 |
| D6 | `g2s-core` 零依赖，Spark 作为可选适配器 | 没装 Spark 的机器也能跑，只是校验档位低一档 |
| D7 | 工具只读 JSON，规则库由脚本生成索引 | 避免为读 YAML 引入第三方库 |
| D8 | 默认阻断，只有 `auto` 自动放行 | 用户明确要求；宁可不出结果，也不出结论不明的 SQL |
| D9 | 版本覆盖冻结为 Spark 4.2.0 | 版本间行为确有差异，冻结才能给出确定结论 |
| D10 | 所有规则结论必须实测 | 实测已推翻多处直觉假设，见 §13 的实测清单 |

## 13. 待验证清单

以下项目前**尚未完成或未验证**，使用前需要留意：

1. **Spark 接入未实现**。`g2s-spark` 适配器只有目录骨架，因此校验档位当前只到
   `static-only`：转换结果的语法未被 Spark 4.2.0 解析器验证过。这是当前最大的缺口。
2. **真实模型端到端演练尚未执行**。`tests/run_e2e_tests.sh` 用的是预制记录，
   验证的是工具链与闸门，不是模型在真实语料上的表现。
3. **PL 块的启发式切分路径没有测试覆盖**。现有语料的 PL 块都带美元引用，
   靠 `BEGIN/END` 计数的分支未经验证。
4. **opencode / trae / codebuddy 的技能目录约定未实测**，适配层映射表待补。
5. **大文件（数万行）未做实测**，阈值设定与内存表现待验证。
6. **Spark 4.2.0 之外版本未验证**，包括 4.0.x 与 4.1.x 的差异。

已实测确认的关键行为（依据见 `checklist/spark-4.2.0-baseline.md`）：
`numeric` 无精度会被静默截断为 `decimal(10,0)`；排序默认 NULL 位置与 openGauss
完全相反；日期格式串 `SS` 未小写会静默吞掉秒值；`COMMENT ON COLUMN` 语法不被支持；
`DISTRIBUTE BY` 在查询语句中能解析但语义完全不同。

## 14. 演进路线

1. **补齐 Spark 接入**：实现 `g2s-spark` 的 `parsePlan` 与 `EXPLAIN` 校验，
   把校验档位从 `static-only` 提升到 `explain-checked`。
2. **真实语料演练**：用 `tests/local/` 的样例跑真实模型端到端，校准规则库与提示词。
3. **补批量审批**：`DEFAULT nextval(...)` 这类高频构造按模式一次性确认。
4. **补适配层**：实测各 CLI 的技能目录约定，完善 `adapters/`。
5. **建立金样评测集**：把人工确认过的（输入、期望输出、理由）三元组沉淀为回归资产。
