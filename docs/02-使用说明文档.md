# gauss2spark 使用说明

## 1. 适用范围与重要限制（请先读这一节）

**测试覆盖版本：Spark 4.2.0。** 本工具的全部行为结论都来自在 Spark 4.2.0 上的实测。
其他版本（包括 4.0.x 与 4.1.x）的行为可能不同，**不承诺正确性**；
如需支持其他版本，请按第 10 节的方法先用基线工具重跑一遍。

适用与不适用：

| 项 | 说明 |
|---|---|
| 支持的源方言 | openGauss，`DBCOMPATIBILITY = PG` |
| 支持的目标方言 | Spark SQL 4.2.0 |
| 支持的语句 | SELECT、常用 DML 与 DDL、`COMMENT ON`、`SHOW`、`EXPLAIN` 等 |
| **不支持** | PL 块（`DO`、`FUNCTION`、`PROCEDURE`、`TRIGGER`）、psql 元命令 |
| 不绑定落点 | 不生成 `USING`、`TBLPROPERTIES` 等存储相关子句 |

另外两条必须知道的性质：

1. **结果可追溯，但不可复现**。同一输入两次运行可能得到不同结果。
2. **默认阻断**。只有低风险确定性转换会自动放行，其余一律需要人工确认；
   未确认完不会产出最终 SQL。

## 2. 环境要求

| 组件 | 要求 | 说明 |
|---|---|---|
| JDK | 17 及以上 | 运行工具；若同时用 Spark，Java 17 也是 Spark 4.x 的要求 |
| Python 3 | 3.9 及以上 | 仅用于规则库校验与索引生成，不参与转换 |
| PyYAML | 任意近期版本 | 同上 |
| Spark | 可选 | 当前版本暂未接入，见第 9 节 |

工具构建产物不入库，第一次使用需要先构建：

```bash
tools/build.sh          # 只需 JDK，不需要联网
```

## 3. 快速开始

```bash
# 1. 构建工具
tools/build.sh

# 2. 准备这次运行的工作目录
RUN=runs/$(date -u +%Y%m%dT%H%M%S)-demo
mkdir -p "$RUN"
cp 你的文件.sql "$RUN/00_input.sql"

# 3. 切分，得到语句清单与路由判定
./g2s split --in "$RUN/00_input.sql" --out "$RUN"

# 4. 依次执行四个节点（在 CLI 中调用对应 skill）
#    gauss2spark-analyze → gauss2spark-convert → gauss2spark-review →（必要时）gauss2spark-fix

# 5. 契约校验与闸门
./g2s check --run "$RUN"
./g2s gate  --run "$RUN"

# 6. 人工确认后组装产物
./g2s assemble --run "$RUN" --model-host claude --model-name 你的模型 \
    --verification-tier static-only
```

## 4. 分阶段执行

每个节点都可以单独跑、单独检查，全部通过 run 目录里的文件交接。

| 节点 | 产物 | 说明 |
|---|---|---|
| split | `statements.jsonl`、`split_summary.json` | 切分、编号、偏移、路由判定 |
| analyze | `01_analysis.jsonl` | 分类、风险、档位、命中的规则 |
| convert | `02_conversion.jsonl` | 改写结果 + 决策链（过程文档的数据源） |
| review | `03_review.jsonl` | 独立复核结论与 findings |
| fix | `04_fix.jsonl` | 按 findings 的修复记录，最多 2 轮 |

中断后可以从中断处继续：所有阶段都只依赖 run 目录里已有的文件。

## 5. 大文件处理

切分器按"行数或语句数"双条件路由：

| 条件 | 路由 | 处理方式 |
|---|---|---|
| ≤ 200 行且 ≤ 20 条语句 | `direct` | 整个文件直接交给模型 |
| > 200 行或 > 20 条语句 | `split` | 按语句分片处理，逐条留痕 |

阈值可以在 `split` 上调整：

```bash
./g2s split --in "$RUN/00_input.sql" --out "$RUN" --max-lines 500 --max-statements 50
```

## 6. 阻断项与人工确认

运行 `./g2s gate --run "$RUN"` 会列出所有待处理语句与原因。退出码含义：

| 退出码 | 含义 |
|---|---|
| 0 | 放行 |
| 1 | 契约校验有错误（记录不完整、引用不存在的规则等） |
| 2 | 命令用法错误或路径不存在 |
| 3 | 闸门未放行（有语句待确认或无法转换） |

确认记录写在 `$RUN/approvals.jsonl`，每行一条：

```json
{"statement_id":"s0007","action":"accept-converted","by":"张三","at":"2026-09-30T18:00:00+08:00","note":"键值改由写入侧生成，已确认","manual_sql":""}
```

三种处置：`accept-converted` 接受转换结果、`use-manual` 改用你提供的人工 SQL
（此时 `manual_sql` 必填）、`exclude` 排除该语句（最终文件里留一行说明）。

**高频构造建议批量确认。** 真实语料里 `DEFAULT nextval(...)` 几乎出现在每个建表语句中，
按构造一次性确认键值生成策略，比逐条处理快得多。

确实需要先拿到残缺结果时，加 `--allow-partial`，此时最终 SQL 头部会带醒目的
`[BLOCKED]` 提示，禁止直接执行。

## 7. 规则库维护

规则库在 `rules/`，按主题分文件。改动流程：

```bash
# 1. 改 YAML（新增/修改/停用规则）
# 2. 重新生成机器可读索引
python3 tools/gen_rule_index.py
# 3. 校验结构与一致性
python3 tests/validate_rules.py
```

校验器会检查：YAML 可解析、字段齐全、枚举取值合法、规则 id 唯一、
**重复键**（YAML 默认静默覆盖，这里当错误处理）、高风险改写规则不得自动放行、
索引指向的文件存在、`rules/index.json` 与规则库一致。

档位的含义：

| 档位 | 含义 | 闸门行为 |
|---|---|---|
| `auto` | 确定性转换、低风险 | 自动放行 |
| `confirm` | 可转换但语义有偏差或依赖前置条件 | 需人工确认 |
| `blocked` | 无法转换 | 需人工改写或排除 |

新增规则时注意：没有实测依据的规则状态只能是 `candidate`，不得直接 `enabled`；
每条 `rewrite` 规则必须有 `examples`；同一条规则的内容变更要递增 `version`。

## 8. 过程文档与审计

每次运行产出：

| 文件 | 内容 |
|---|---|
| `05_final.sql` | 最终 SQL（仅放行或 `--allow-partial` 时产出） |
| `06_process-log.md` | 转换过程文档：全部语句一览 + 需细读语句的完整决策链 |
| `07_audit-report.md` | 审计报告：统计、自由发挥清单、规则使用、阻断与确认记录 |
| `08_report.html` | 对照报告：语句一览加逐句左右对照，浏览器直接打开 |
| `run_manifest.json` | 运行清单：输入哈希、规则集哈希、闸门统计、校验档位 |
| `trace.jsonl` | 追加式事件流 |

**机器可读记录永远全量**，过程文档只是它的可读视图——文档为控制篇幅只详述
非 `auto` 档和有 findings 的语句，但任何一条语句的决策都能在 JSONL 里查到。

## 9. 结果验证

当前工具链的校验档位是 `static-only`，即：结构检查、方言残留扫描、契约校验。
**转换结果的语法尚未被 Spark 解析器验证过**，语义等价性也未经过执行验证。

因此把结果用于生产前，请在一侧有真实环境时自行完成：

1. 用目标 Spark 版本解析每条语句（语法层）。
2. 用真实建表语句建立空表，对每条语句执行 `EXPLAIN`（列名、类型、函数是否存在）。
3. 有数据时，对关键查询做行数与聚合校验和比对。

第 2 步不需要数据、也不需要集群，是性价比最高的一档。
把每次实际用到的档位记进 `run_manifest.json` 的 `verification_tier` 字段。

## 10. 换目标 Spark 版本

1. 下载并解压目标版本的 Spark 发行包。
2. 用基线工具重跑一遍行为实测：

```bash
SPARK_HOME=/path/to/spark
javac -cp "$SPARK_HOME/jars/*" -d /tmp/probe validation/SparkBaselineProbe.java
jar cf /tmp/probe.jar -C /tmp/probe .
"$SPARK_HOME/bin/spark-submit" --class SparkBaselineProbe --master 'local[1]' /tmp/probe.jar
```

注意 Spark 本地模式需要创建本地 socket，在受限沙箱中会失败，需在普通终端执行。

3. 逐条比对差异，新建 `checklist/spark-<版本>-baseline.md`，
   并据此修订规则库中标注 `scope.spark` 的条目。

## 11. 常见问题

**转换结果里有 `numeric` 没带精度？** 必须补。Spark 会把它当成 `decimal(10,0)`，
既不报错又会丢数据，这是本项目发现的最危险的一处静默错误。

**`ORDER BY` 为什么都被加了 `NULLS LAST`？** 因为 Spark 与 openGauss 的默认 NULL
位置完全相反，不补就会静默改变结果顺序。

**`decode`、`nvl`、`string_agg` 为什么没有改写？** 它们在 Spark 4.2 上原生可用且
语义一致，改写只会增加风险。规则库的 `core.functions.native` 专门禁止这类改写。

**源文件是 GBK 编码会乱码吗？** 不会，编码按 BOM、UTF-8、GB18030、Latin-1 顺序
自动探测，实际使用的编码记录在 `split_summary.json` 里。

**为什么缺少 `05_final.sql`？** 闸门未放行。先看 `g2s gate` 输出的待处理清单。

## 12. 命令与产物速查

```bash
tools/build.sh                                  # 构建工具
python3 tools/gen_rule_index.py                 # 重新生成规则索引
python3 tests/validate_rules.py                 # 校验规则库
python3 tests/validate_skills.py                # 校验 skill 与跨文件引用
tests/run_splitter_tests.sh                     # 切分器回归
tests/run_e2e_tests.sh                          # 端到端回归（含闸门与组装）

./g2s split    --in <file> --out <run_dir>
./g2s check    --run <run_dir>
./g2s gate     --run <run_dir>
./g2s assemble --run <run_dir> [--allow-partial] [--model-host X] [--model-name Y] \
               [--verification-tier static-only]
./g2s version
```

产物清单：`00_input.sql`、`statements.jsonl`、`01_analysis.jsonl`、
`02_conversion.jsonl`、`03_review.jsonl`、`04_fix.jsonl`、`approvals.jsonl`、
`05_final.sql`、`06_process-log.md`、`07_audit-report.md`、`08_report.html`、
`run_manifest.json`、`trace.jsonl`。字段定义见 `contracts/artifact-contract.md`。
